# life_agent

Персональный агент для управления жизнью: календарь, нагрузка недели, риск выгорания и цели. Сервер на Go, клиент на Flutter (Android и macOS).

> **Это полностью вайбкод-проект.** Ни одна строка кода не написана руками. Весь код, тесты, скрипты выкладки и документация созданы ИИ-агентом в режиме агентной разработки. Человек ставил задачи, принимал решения, проверял результат и делал коммиты.

## Что умеет

- Пишешь или надиктовываешь фразу («КВН в пятницу с 18 до 20», «курсовая, 6 часов, до пятницы»). Агент разбирает её в событие или задачу.
- Смотрит Google Calendar и нагрузку недели, отвечает, можно ли добавить, и объясняет почему.
- После подтверждения записывает событие в календарь.
- Раскладывает задачи с дедлайнами по неделе. План строит код, детерминированно.
- Следит за четырьмя рисками выгорания: недосып, перегруз учёбой, нет отдыха, плохое состояние по чек-ину.
- Собирает картину дня без ручной разметки: экранное время телефона и Mac, Steam, GitHub, LeetCode, сон и тренировки из Health Connect, погода. Сопоставляет её с четырьмя целями: учёба, карьера, спорт, работа.
- Даёт советы, когда нагрузка выше порога или состояние красное.

Главный принцип: всё, что можно сделать кодом, делает код. LLM только извлекает части фразы и пишет текст совета. Даты, пересечения, метрики, план недели и решение «выдавать ли совет» считает код. Используются только бесплатные модели OpenRouter (`:free`) с цепочкой резервных моделей.

## Стек

| Часть | Технологии |
|-------|-----------|
| Сервер | Go, один статический бинарник, SQLite (`modernc.org/sqlite`, без CGO) |
| Клиент | Flutter: Android (основная платформа), macOS |
| Mac-агент | Консольная программа на Go, читает ActivityWatch, запускается через launchd |
| Календарь | Google Calendar API через сервисный аккаунт |
| LLM | OpenRouter, бесплатные модели, провайдеро-независимый роутер |
| Хостинг | VPS, systemd, nginx, Let's Encrypt |

## Структура

```
PLAN.md        полный план проекта: решения, этапы, правила для агента
CLAUDE.md      короткие правила проекта, которые агент читает при каждом запуске
server/        Go-бэкенд (cmd/server, cmd/macagent, internal/...)
app/           Flutter-приложение
deploy/        systemd-юниты, конфиг nginx, скрипты выкладки и бэкапа
docs/          инструкции для ручных шагов и дизайн-бриф
```

## Запуск

Сервер:

```bash
cp .env.example .env   # заполнить ключи
cd server && go test ./... && go run ./cmd/server
```

Приложение:

```bash
cd app && flutter test && flutter build apk
```

Выкладка на сервер описана в `deploy/deploy.sh` (`bootstrap`, `env`, `release`, `nginx`, `app`). Ручные шаги подготовки (сервисный аккаунт Google, ключ OpenRouter) описаны в `docs/STAGE0.md`.

## Агентная разработка

Проект собран ИИ-агентом (Claude Code). Агентная разработка отличается от чата с подсказками кода: агент сам работает в репозитории и терминале, а человек управляет им через задачи, правила и проверку результата.

### Как это устроено

1. **План как источник правды.** Перед кодом был написан `PLAN.md`: цель, принятые решения, модель данных, API, этапы, критерии готовности, тесты, безопасность. План адресован агенту. Агент читает его перед работой и не пересматривает принятые решения без причины.
2. **Правила проекта.** `CLAUDE.md` и раздел 12 плана задают границы: не выводить ключи в чат, не добавлять функции вне плана без согласования, не писать в календарь без подтверждения, не трогать чужие сервисы на сервере.
3. **Цикл агента.** На каждую задачу агент сам проходит цикл: читает код → планирует изменение → правит файлы → запускает тесты и сборку → читает ошибки → исправляет → повторяет, пока проверки не пройдут.
4. **Этапы с приёмкой.** Работа разбита на этапы (0–10). Каждый этап заканчивается результатом, который человек проверяет сам. Агент в конце этапа говорит, что проверить руками.
5. **Тесты как ограждение.** Агент не «верит» своему коду. Логика покрыта табличными тестами Go (`go test ./...`), LLM в тестах заменена заглушкой. Качество разбора фраз меряется эталонным набором фраз при каждой смене модели или промпта.
6. **Человек в контуре.** Опасные действия идут только после подтверждения: любые изменения на сервере (сначала только чтение, потом показ команд), запись в календарь, установка инструментов. Решения о продукте и архитектуре принимает человек.

### Почему агент не коммитит

Агент не делает коммиты, а в истории нет строк вроде `Co-Authored-By` с его именем. Автор всех коммитов — человек.

Это ограничение сделано, чтобы мусорный сгенерированный код не попадал в историю версий. Агент быстро пишет много кода, и часть его оказывается промежуточной: пробные варианты, лишние правки, код, который потом переписан. В git попадает только то, что человек посмотрел, проверил и принял. История остаётся чистой: каждый коммит — осмысленное принятое изменение, а не след каждой попытки агента.
