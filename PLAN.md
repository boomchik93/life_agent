# План: персональный агент для управления жизнью

Документ написан для Claude, который будет собирать проект. Читай его целиком перед началом работы. Пользователь один, приложение только для личного использования, публикации не будет.

## 1. Цель

Пользователь надиктовывает или пишет событие («КВН в пятницу с 18 до 20») или задачу с дедлайном («курсовая, 6 часов, до пятницы»). Агент:
1. разбирает фразу в структуру (LLM извлекает части, дату и время считает код);
2. смотрит Google Calendar и нагрузку недели;
3. определяет категорию (учёба или нет);
4. отвечает, можно ли добавить, и объясняет почему;
5. по подтверждению пользователя записывает событие в календарь;
6. раскладывает задачи с дедлайнами по неделе (это делает код, не LLM);
7. следит за риском выгорания.

Выгорание в этом проекте означает четыре риска: **недосып**, **перегруз учёбой без перерывов**, **нет развлечений и отдыха**, **плохое состояние** (низкая энергия и настроение по ежедневному чек-ину). Чек-ин — единственный прямой сигнал мотивации, остальные метрики косвенные.

Расширение (этап 10): цель проекта шире, чем защита от выгорания. Агент помогает больше достигать и развиваться, а не прокрастинировать. Для этого он автоматически собирает картину жизни (экранное время телефона и компьютера, игры, GitHub, LeetCode, сон, тренировки, погода) и сопоставляет её с четырьмя равноценными целями: учёба, карьера, спорт, работа. Пользователь ничего не размечает и не отмечает вручную. Риски выгорания остаются ограничителем: цель не планируется поверх красного риска.

## 3. LLM

Всё, что можно сделать обычным кодом, делается кодом без LLM. Платные API не используются: единственный провайдер — OpenRouter с бесплатными моделями `:free`. Claude и другие платные модели в проекте не задействованы.

| Задача | Исполнитель | Модель по умолчанию |
|--------|-------------|---------------------|
| Расчёт даты и времени из частей фразы, проверка слота, пересечения, подсчёт часов, правила нагрузки, план недели, решение «выдавать ли совет» | Код | нет |
| Извлечение частей фразы в структуру (раздел 13) | LLM | Бесплатная модель OpenRouter (`:free`), выбирается на этапе 5 по эталонному набору |
| Категория | Поле `category_guess` из ответа разбора, поверх него память категорий по нормализованному названию. Отдельного вызова LLM нет | нет |
| Текст совета | LLM | Бесплатная модель OpenRouter, настраивается |

### Выбор модели, эффорта и резервных моделей

- В настройках приложения для каждой LLM-задачи (разбор, совет) три поля: **модель**, **эффорт** (`low` / `medium` / `high`) и **цепочка резервных моделей** (упорядоченный список id).
- Модель выбирается из списка или вводится id вручную. Список собирается из API моделей OpenRouter и кэшируется на сервере.
- Эффорт показывается только для моделей с рассуждением. Признак берётся из метаданных OpenRouter (поддерживаемые параметры в списке моделей). Адаптер провайдера переводит эффорт в параметр API (`reasoning`). Названия параметров сверить с актуальной документацией.
- Конфиг по умолчанию лежит в файле, правки пользователя хранятся в БД и перекрывают его. Смена модели, эффорта и цепочки работает без перезапуска сервера.

### Резервные модели и повторы

Запрос уходит на следующую модель цепочки, если:
- модель вернула невалидный JSON (проверка по схеме) и повтор с текстом ошибки тоже не помог;
- упёрлись в лимит бесплатной модели или таймаут;
- ответ не прошёл проверку кодом (раздел 13).

Повтор на той же модели: один раз при невалидном ответе (в промпт добавляется текст ошибки), при лимите без повтора. Если цепочка исчерпана, пользователь получает понятное сообщение, введённый текст сохраняется.

Два вида лимита обрабатываются по-разному:
- **Лимит или перегрузка конкретной модели** (429 от модели, «нет доступных эндпоинтов», таймаут): переход на следующую модель цепочки.
- **Дневной лимит аккаунта на бесплатные модели**: он общий для всех `:free`-моделей, поэтому переход по цепочке не поможет и только сожжёт попытки. Цепочка сразу останавливается, пользователь видит «дневной лимит исчерпан, сброс в <время>». Как отличить эти ответы, сверить с актуальной документацией OpenRouter.

### Бюджет запросов

Без пополнения у аккаунта порядка 50 запросов к `:free`-моделям в сутки и порядка 20 в минуту (сверить актуальные лимиты). Каждый повтор и переход по цепочке тратит запрос, поэтому:
- Один пользовательский запрос тратит не больше 4 вызовов LLM в сумме (раздел 14). Цепочка резервных моделей — не длиннее 3 моделей.
- Сервер считает вызовы за сутки по `llm_calls` и показывает остаток в настройках.
- Автосовет не запускается, если остаток меньше 10 запросов: квота важнее для разбора фраз.
- Категоризация названий (этап 10) идёт пачкой до 30 названий за один вызов, не больше 2 вызовов в сутки, источник `auto`, и тоже не запускается при остатке меньше 10 запросов. Неразобранные названия ждут следующих суток и до тех пор остаются `unknown`.
- Прогоны эталонного набора помечаются в `llm_calls` отдельно (`source = eval`) и идут с паузой, чтобы не упереться в минутный лимит. Полный прогон 30–50 фраз почти съедает дневную квоту без пополнения. Его надо либо дробить по дням, либо пополнить счёт на $10 на время подбора модели (раздел 19).

Пакет `internal/llm`, функция `Call(ctx, task, schema)`. Все вызовы идут только через него. Провайдер — реализация интерфейса `openai_compatible` (OpenRouter; другие провайдеры с OpenAI-совместимым API добавляются конфигом).

### Журнал вызовов

Каждый вызов пишется в `llm_calls`: время, задача, провайдер, модель, задержка, токены, результат (`ok` / `invalid_json` / `check_failed` / `timeout` / `limit`), номер попытки, номер модели в цепочке, источник (`user` / `auto` / `eval`). Тексты запросов и ответов не пишутся. По журналу видно, что модель деградировала.

### Приватность

- Бесплатные провайдеры могут логировать запросы и использовать их для обучения.
- В разбор уходят только текст фразы, текущая дата и часовой пояс.
- В совет по умолчанию уходит только сводка нагрузки: часы по категориям, цвета календарных рисков, причина совета. Данные чек-ина и здоровья (энергия, настроение, сон) в модель не отправляются. Включается отдельным переключателем в настройках с предупреждением, что запрос может логироваться провайдером. Без него причина «состояние красное» передаётся словами без цифр.
- Категоризация неизвестных приложений, игр и доменов (этап 10): в модель уходят только названия (приложения, игры, домена), без времени и других данных использования. Пользователь с этим согласен. Названия считаются недоверенным вводом: ответ принимается только как значение из фиксированного списка категорий, остальное отбрасывается. Результат кэшируется в `app_category` навсегда. Переключатель в настройках отключает отправку названий, тогда остаются локальные слои и `unknown`.

### Ключи

Ключ нового проекта (OpenRouter) создаётся отдельно и лежит в `.env` нового проекта. Ключи из `/opt/calendar-pwa/.env` не читать и не копировать без явного разрешения пользователя.

## 4. План недели: алгоритм (код, без LLM)

Раскладка задач по слотам — задача с ограничениями. Код решает её детерминированно: один и тот же вход даёт один и тот же план, без нарушений правил.

Вход: открытые задачи (`kind = task`: длительность, дедлайн, категория, приоритет), занятые слоты из всех календарей и ICS, правила нагрузки.

1. Построить свободные окна на неделю: вычесть окно сна, занятые слоты, обязательные свободные вечера (раздел 14).
2. Отсортировать задачи по дедлайну, затем по приоритету.
3. Класть задачи кусками (по умолчанию от 30 мин до 2 ч) в самые ранние подходящие окна. Не превышать лимит учёбы подряд и в день, между кусками учёбы оставлять перерыв.
4. Если задача не помещается до дедлайна, она попадает в список `unplaced` с числом недостающих минут. Правила ради неё не нарушаются.
5. Итоговый план прогоняется через тот же валидатор, что и в тестах.
6. Пользователь видит предпросмотр. В календарь ничего не пишется без подтверждения. Существующие события не двигаются.

Как это сделано (этап 7):
- Планируется неделя с понедельника по понедельник, начиная с ближайших 15 минут после «сейчас». Задачи с дедлайном позже этой недели в план не попадают и показываются отдельным списком (`deferred`); они ложатся в план своей недели.
- Остаток задачи = длительность минус минуты уже записанных кусков (таблица `plan_chunks`). Записанные куски считаются сделанными, отдельно отмечать их не нужно.
- Лимиты учёбы в плане равны «жёлтым» порогам раздела 14 (6 ч в день, 3 ч подряд, 35 ч в неделю), считая уже стоящие в календаре события. План не делает учёбу жёлтой.
- Свободные вечера защищаются с конца недели: последние свободные вечера остаются без кусков, пока их не станет `FreeEveningsMin`.
- Сервер не собирает и не записывает план, если не прочиталась хотя бы одна запись о занятости (календарь или ICS).
- Перед записью сервер заново проверяет присланный план валидатором на актуальных данных; устаревший план отклоняется (`plan_stale`).
- Настройки планировщика: ключ `plan_params` (`sleep_start_hour`, `sleep_end_hour`, `chunk_min_min`, `chunk_max_min`).

## 5. Советы по выгоранию

Совет выдаётся в двух случаях:
- пользователь просит сам (кнопка или фраза в вводе);
- автоматически, если прошло больше N дней с прошлого совета (по умолчанию 7) **и** выполнено хотя бы одно: нагрузка выше порога (часы и число событий за неделю, недосып) или состояние по чек-ину красное.

N и пороги настраиваются. Условия проверяет код, модель вызывается только когда решение выдать совет уже принято. Доставка: сервер готовит совет, фоновая задача приложения забирает его через `GET /v1/advice/pending` и показывает локальное уведомление.

## 6. Метрики нагрузки

Каждому риску присваивается цвет: зелёный, жёлтый, красный. Нет данных — серый «нет данных», цвет не угадывается.

- **Недосып**: реальные часы сна из Health Connect. Пока их нет — часы сна из чек-ина. Промежуток между событиями календаря как оценку сна не использовать.
- **Перегруз**: часы событий категории `study` за день и неделю, часы подряд без перерыва. Учёба вне календаря не видна, поэтому метрика — нижняя оценка. Планировщик уменьшает эту проблему: учебные задачи попадают в календарь.
- **Нет отдыха**: часы событий категорий `sport`, `hobby` и `rest` за неделю и число свободных вечеров (без событий после 18:00).
- **Состояние**: среднее энергии и настроения по чек-ину за последние 3 дня.

Правила подсчёта:
- Повторяющиеся события читаются развёрнутыми в экземпляры (`singleEvents=true`).
- События на весь день не входят в подсчёт часов.
- Часы считаются в часовом поясе пользователя, переходы на летнее время учитываются библиотекой `time`, а не руками.

Если событие делает любой риск красным, агент не добавляет его без явного подтверждения.

Источники занятости: все календари из конфига и ICS-ссылка с расписанием пар (если она есть). Подключаются на этапе 2, а не после правил нагрузки.

## 7. Модель данных (черновик)

События календаря в БД не копируются (раздел 2).

- `settings`: ключ-значение (модели, пороги, N дней, список календарей, ICS-ссылка, часовой пояс).
- `items`: разобранные запросы. `kind` = `event` (фиксированное время) или `task` (длительность и дедлайн). Поля: название, категория; для `event` начало, конец, `recurrence`; для `task` `duration_min`, `deadline`, приоритет. Статус: `draft` / `confirmed` / `written` / `done`. `idempotency_key`, список `event_id` в календаре.
- `category_memory`: нормализованное название (нижний регистр, без дат, времени, дней недели и предлогов) → категория, источник (ответ пользователя или модель), число подтверждений.
- `checkins`: дата, энергия 1–5, настроение 1–5, часы сна (если нет данных Health Connect).
- `health_daily`: дата, часы сна, средний пульс, стресс, пульс покоя, шаги, минуты тренировок. Только сводки.
- `advice_log`: время, причина, текст совета, статус доставки.
- `llm_calls`: раздел 3, без текстов.
- `activity_daily` (этап 10): дата, источник (`android_usage`, `mac_activitywatch`, `steam`, `github`, `leetcode`, `weather`), категория, минуты, количество, уверенность, `extra` (JSON). Уникальность по (дата, источник, категория). Только сводки.
- `app_category` (этап 10): нормализованный идентификатор (пакет Android, домен, `steam:<appid>`, имя приложения Mac) → категория, происхождение (`android_meta`, `dictionary`, `steam_genre`, `context`, `llm`), уверенность, дата. Данных использования не содержит.
- `source_state` (этап 10): источник, включён ли, время последней синхронизации, последняя ошибка.
- `goals` (этап 10): цель (`study`, `career`, `sport`, `work`), недельная норма в минутах (может быть пустой), происхождение нормы (`auto` / `confirmed`), дата пересчёта.
- `weekly_review` (этап 10): начало недели, результат расчёта (JSON).

## 8. API (черновик)

Все пути под `/v1`, все с токеном.

- `POST /v1/parse`: текст → структура (`event` или `task`) с уже рассчитанными кодом датами.
- `POST /v1/check`: структура → вердикт (можно или нет, пересечения, категория, цвета рисков до и после, причины).
- `POST /v1/events`: подтверждённое событие → запись в календарь. Обязателен заголовок `Idempotency-Key`; повтор с тем же ключом возвращает уже созданное событие, а не создаёт второе.
- `POST /v1/items`, `GET /v1/items?kind=task&status=open`, `PATCH /v1/items/{id}`: задачи с дедлайнами.
- `GET /v1/week`: события недели и оценка рисков.
- `POST /v1/plan/week`: предпросмотр раскладки (`placed`, `unplaced`).

## 9. Хостинг и изоляция от других проектов

На сервере `cv-prod` уже живут другие проекты: `calendar-pwa` (Go, порт 8090, systemd), `alpha26` (Docker, порты 18000 и 18001), `cv-site` (Docker, порт 8080), `gitsim`. Ресурсы тесные: 1 CPU, 1,9 ГБ RAM (около 1,3 ГБ доступно), 50 ГБ диска. Этот проект не должен им мешать.

Правила:

- Каталог `/opt/life-agent`, отдельный системный пользователь `lifeagent` без shell, отдельный systemd-юнит `life-agent.service`.
- В юните лимиты: `MemoryMax=300M`, `CPUQuota=50%`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ReadWritePaths=/opt/life-agent/data`.
- Приложение слушает только `127.0.0.1:18010`. Перед первым запуском проверить, что порт свободен (`ss -tlnp`).
- Бинарник собирается на маке (`GOOS=linux GOARCH=<архитектура сервера> CGO_ENABLED=0`) и копируется на сервер. На сервере ничего не собирать.
- HTTPS: новый отдельный файл nginx `/etc/nginx/sites-available/life-agent` и ссылка в `sites-enabled`. Хост вида `life.144-31-165-229.sslip.io` (резолвится сам, DNS не нужен). Сертификат через `certbot --nginx -d <хост>`. Если Let's Encrypt откажет из-за лимитов sslip.io, использовать поддомен `semenovm.ru`. Basic auth не нужен, проверка токена на стороне Go.
- Существующие файлы nginx (`cv`, `calendar-pwa`) и их сертификаты не менять. Перед перезагрузкой nginx всегда `nginx -t`, перезагрузка только `systemctl reload nginx`.
- Свой файл SQLite в `/opt/life-agent/data`. Общие БД и сервисы сервера не использовать.
- Никаких глобальных изменений: не обновлять системные пакеты, не менять firewall, не перезапускать чужие сервисы и контейнеры, не трогать чужие каталоги. `/opt/calendar-pwa` и его `.env` не читать, кроме случая, когда пользователь разрешил явно.
- Перед каждым действием на сервере, кроме чтения, показать пользователю команды и дождаться подтверждения. Сначала только чтение.
- Секреты (`.env`, ключ сервисного аккаунта) лежат в `/opt/life-agent` с правами `600`, владелец `lifeagent`.
- Бэкап на сервере: ежедневная копия файла БД (через `sqlite3 .backup` или `VACUUM INTO`, не простым копированием открытого файла) в `/opt/life-agent/backup`, срок хранения 14 дней (systemd timer), права `600`.
- Бэкап вне сервера: скрипт `deploy/pull-backup.sh` забирает последнюю копию на мак по `scp`. Копия на том же диске бэкапом не считается. В копии есть данные здоровья, хранить её в каталоге с правами `700`.
- Swap на сервере не добавлять без отдельного согласия пользователя.

Как это сделано (этап 8):
- Сводка дня: `date` — день пробуждения. Сон = объединение стадий сна ночи, закончившейся в этот день и начавшейся после 18:00 накануне; если часы не дают стадий, берётся сессия сна. - Проверка, что Samsung Health отдаёт сон в Health Connect, делается руками на S21+: экран «Настройки → Здоровье → Отправить сейчас» покажет, нашлись ли сон и пульс.
- Доступ проверяется по видам данных (сон, пульс, пульс покоя, тренировки, шаги) отдельно. Хватает любого: без доступа к виду его поле просто не отправляется. Экран «Здоровье» показывает список «Что подключено» с отметкой по каждому виду и по чтению в фоне, кнопку «Запросить недостающее» и после отправки — что именно ушло за каждый день.

### Этап 9. Советы и macOS
- Советы по разделу 5, `GET /v1/advice/pending`, локальные уведомления из фоновой задачи, сборка под macOS.
- **Готово, когда:** совет приходит по запросу и по условиям раздела 5, уведомление появляется без открытия приложения.

Как это сделано (этап 9):
- Условия автосовета проверяет код (`internal/advice`): с прошлого совета прошло больше `interval_days` (7) и есть причина: перегруз жёлтый или красный, недосып жёлтый или красный, состояние красное, событий в неделе больше `events_week_above` (30). Серый цвет причиной не бывает. Настройки лежат в ключе `advice` (`interval_days`, `events_week_above`, `include_private`, `min_quota`).

Готовый совет ждёт, пока телефон заберёт его через `GET /v1/advice/pending`; отдаётся один раз, поэтому уведомление не повторяется. Совет «по просьбе» (`POST /v1/advice`, кнопка или фраза «дай совет» в вводе) интервал и резерв квоты не проверяет.

- Ответ проверяется кодом: JSON `{"text": ...}`, до 600 символов, до трёх предложений, русский. Не прошёл: один повтор, затем следующая модель цепочки.
- Фоновая задача раз в 6 часов делает и отправку здоровья (если включена), и забор совета с локальным уведомлением (если включено).

- Клиенты (телефон, Mac) шлют `POST /v1/activity/daily` со строгой схемой: источник, день, строки `category`, `minutes`, `night_minutes`, `count`, `confidence`. Любое другое поле (название окна, URL, имя приложения) отклоняется на разборе, до БД и логов. Новая сводка того же дня и источника заменяет старую.
- Серверные источники (Steam, GitHub, LeetCode, погода) идут через интерфейс `activity.Collector` и `activity.Run`: строки проверяются все вместе до записи, ключ `extra` ограничен словарём (числа и до пяти коротких жанров), ошибки сохраняются без URL (в URL может быть ключ API).
- Бэкапы: при `AGE_RECIPIENT` в `.env` на сервере остаётся только `*.db.age`; `deploy/pull-backup.sh` расшифровывает копию на маке приватным ключом (`age-keygen -o ~/.config/life-agent/age-key.txt`, `brew install age`).
- Хранение дневных сумм 365 дней, чистка раз в сутки.
- Экспорт `GET /v1/export`; `DELETE /v1/data` требует `{"confirm":"delete-all-data"}` и стирает данные, но не настройки.

**10.1 Телефон: UsageStats**
- Разрешение «Доступ к истории использования» (выдаётся вручную один раз, инструкция в приложении). Чтение `UsageStatsManager` в фоновой задаче этапа 8. Время по приложениям переводится в категории по слоям, на сервер уходят минуты по категориям и ночные минуты (в окне сна раздела 14) через `POST /v1/activity/daily`. Названия приложений уходят только в `POST /v1/categorize` и только для неизвестных. Сырые данные на телефоне не хранятся дольше отправки.
- **Готово, когда:** без открытия приложения за сутки в `activity_daily` появляются минуты по категориям, доля `unknown` ниже 20 %.

Как это сделано (шаг 10.1):
- Чтение `UsageStats` — свой плагин `app/packages/life_usage` (Kotlin), чтобы он был и в фоновом изоляте WorkManager. Он отдаёт только сессии «пакет, начало, конец» и `ApplicationInfo.category`. Разрешения `PACKAGE_USAGE_STATS` (выдаётся вручную, инструкция на экране «Источники») и `QUERY_ALL_PACKAGES` (иначе Android 11+ скрывает чужие приложения от поиска категории).
- Порядок слоёв на телефоне: категория Android, если уверенность не ниже 0,7 (игры, видео, музыка, соцсети, новости); иначе словарь и кэш сервера без модели (`POST /v1/categorize` с `llm:false`); затем контекст календаря (время внутри события study, work, hobby или rest получает его категорию, уверенность 0,9); и только для оставшегося времени неизвестных приложений вопрос к модели. Приложение, о котором сервер уже ответил «неизвестно», повторно не спрашивается.
- На сервер уходят минуты по категориям, ночные минуты (окно сна 23:00–07:00) и средняя уверенность. Названия пакетов уходят только в `/v1/categorize`, и только те, что не определились локально. Сырые сессии живут внутри одного вызова синхронизации.
- `/v1/categorize`: словарь в коде (`internal/appcat/dictionary.go`), кэш `app_category` навсегда, пачка до 30 названий за вызов, не больше 2 вызовов в сутки (`categorize_runs`), не при остатке квоты ниже `min_quota`, переключатель `categorize.llm` (в приложении на экране «Источники»). Ответ модели принимается только как категория из списка; выдуманные ключи, чужие поля и категории вне списка отбрасываются. Уверенность ниже 0,7 кэшируется как `unknown`. Для задачи используется модель `parse` с источником `auto`.
- `GET /v1/week` теперь отдаёт у каждого события `category` (ту, что использует расчёт нагрузки).
- Доля `unknown` после «Отправить сейчас» показывается на экране; выше 20 % — предупреждение.
- Проверить руками на S21+: «Настройки → Источники → Телефон», выдать доступ, «Отправить сейчас», через сутки смотреть, что `activity_daily` пополняется без открытия приложения.

**10.2 Mac: ActivityWatch**
- Пользователь ставит ActivityWatch (`aw-server`, `aw-watcher-window`, `aw-watcher-afk`) и расширение браузера `aw-watcher-web`. macOS-клиент читает REST API на `localhost:5600`, считает минуты по приложениям и доменам, определяет категории по слоям и отправляет только категории и минуты. Заголовки окон и полные URL остаются на Mac. На Mac должен быть включён FileVault (ActivityWatch хранит заголовки и URL локально без шифрования).
- **Готово, когда:** за день на сервере есть сводка по Mac, в теле запроса нет заголовков и URL (проверяется тестом).

Как это сделано (шаг 10.2):
- Клиент для Mac — консольная программа на Go `server/cmd/macagent` (`internal/macagent`), а не приложение Flutter: сборка Flutter под macOS здесь не проверена (нет полного Xcode), а Go собирается без него. Установка: `deploy/mac/install.sh` (собирает, кладёт в `~/.local/bin`, создаёт `~/.config/life-agent/mac.env` с правами 600, ставит задание launchd раз в 6 часов). Скрипт не ставится, если FileVault выключен; `macagent check` проверяет ActivityWatch, токен и FileVault.
- Читает REST API ActivityWatch: корзины `currentwindow`, `afkstatus`, `web.tab.current`. Считается только время «не отошёл» (`not-afk`). Время браузера делится по доменам из `aw-watcher-web`; страницы в режиме инкогнито и время браузера без домена идут в `unknown`, о них никого не спрашивают. Заголовок окна и вкладки используются только чтобы взять домен и сразу отбрасываются.
- Слои те же, что на телефоне: словарь и кэш сервера (`/v1/categorize` с `llm:false`), контекст календаря, затем модель для остатка. На сервер уходят категории, минуты, ночные минуты и уверенность (`mac_activitywatch`); имена приложений и домены уходят только в `/v1/categorize`.
- Тест `TestNothingButCategoriesLeavesTheMac` поднимает поддельные ActivityWatch и сервер и проверяет все тела запросов: ни заголовков, ни путей, ни query, ни схемы `https://`.

**10.3 Сервер: Steam и погода**
- Steam: Web API key и SteamID64 в `.env`, опрос `GetOwnedGames` и `GetRecentlyPlayedGames` раз в 30 минут, дневные часы = разница накопительного времени по игре. Все игры идут в `leisure`, жанры хранятся в `extra`. Если профиль стал приватным, источник получает ошибку в `source_state`, цвет серый.
- Погода: Open-Meteo без ключа, город и координаты вводятся в настройках приложения, кэш 3 часа, в `activity_daily` источник `weather` (температура, осадки, часы светлого времени). Планировщик (этап 7) по возможности кладёт блоки `sport` в сухие светлые окна.
- **Готово, когда:** часы игр за день совпадают с профилем Steam, погода обновляется и город меняется из приложения.

Как это сделано (шаг 10.3):
- Steam (`internal/steam`, ключи `STEAM_API_KEY` и `STEAM_ID` в `.env`): опрос `GetOwnedGames` и `GetRecentlyPlayedGames` раз в 30 минут (из двух берётся большее число). В `steam_snapshots` пишется накопительное время по играм, только когда число изменилось, снимки старше 30 дней удаляются. Первый опрос — точка отсчёта (старое время не считается сегодняшним); игра, появившаяся позже, считается с нуля; меньшее число (сбой API) игнорируется. День = разность значений на конце и начале суток по часовому поясу пользователя. Дневная строка: `leisure`, минуты, число игр, до пяти жанров в `extra` (жанры из `appdetails`, кэш `steam_genres`, до 5 запросов за круг). Названия игр не хранятся. Приватный профиль даёт ошибку в `source_state`, старые дни остаются.
- Ключ не попадает в ошибки и логи: текст ошибки сети заменяется коротким («steam is not reachable»), `activity.SafeError` вырезает URL.
- Погода (`internal/weather`, Open-Meteo без ключа): город вводится на экране «Источники»; сервер сам находит координаты (геокодер Open-Meteo) и сохраняет их вместе с названием в настройке `weather`. Кэш прогноза 3 часа, смена города подхватывается в течение 15 минут. В `activity_daily` источник `weather`, категория `unknown`, минуты 0, в `extra`: `temp_c`, `precip_mm`, `daylight_hours`, `sunrise_h`, `sunset_h` на вчера и 7 дней вперёд. Использовать это окно для блоков `sport` планировщик будет на шаге 10.6.
- Ключи источников 10.3–10.4 описаны в `.env.example`.

**10.4 Сервер: GitHub и LeetCode**
- GitHub: GraphQL `contributionsCollection` раз в день, fine-grained токен только на чтение; коммиты, PR и ревью по дням в категорию `career`. Для приватных репозиториев в профиле должен быть включён «Include private contributions».
- LeetCode: основной источник — время на `leetcode.com` из браузера (10.2). Запасной и необязательный: публичный GraphQL (число принятых решений по дням); это неофициальный путь, он может сломаться, тогда источник молча отключается и пишет ошибку в `source_state`.
- **Готово, когда:** вклад за вчера совпадает с графиком GitHub.

Как это сделано (шаг 10.4):
- GitHub (`internal/github`, `GITHUB_TOKEN` и `GITHUB_LOGIN` в `.env`): GraphQL `contributionsCollection` раз в сутки за последние три дня. Число за день берётся из `contributionCalendar`, то есть то же, что показывает график профиля (с закрытыми репозиториями при включённом «Include private contributions»). В `extra` лежат разбивка на коммиты, PR и ревью. Строка в категории `career` с `count` и без минут: вклад — это не время. Просроченный токен даёт понятную ошибку в `source_state` («выпусти новый»).
- LeetCode (`internal/leetcode`, `LEETCODE_USER`, по умолчанию выключен): число принятых решений за день из публичного GraphQL, строка `career` с `count`. Время на leetcode.com приходит из браузера (шаг 10.2, словарь). Любая ошибка этого неофициального пути выключает источник сама (`activity.Fragile`) и пишет причину в `source_state`.

Как это сделано (шаг 10.5):

В Health Connect нет типа «стресс», поэтому стресс не используется; если HRV не приходит, его тоже не используем. Результат проверки на реальных Galaxy Watch 4 Classic нужно посмотреть на телефоне.
- Тренировки засчитываются в категорию `sport` при расчёте обзора (шаг 10.6).

**10.6 Цели и недельный обзор**
- Цели: `study`, `career`, `sport`, `work`, равноценные. Недельная норма сначала не задана, цель показывает только факт. Через 14 дней данных сервер предлагает норму (медиана недельных минут +10 %), пользователь подтверждает один раз; пересчёт раз в 4 недели с подтверждением.
- `GET /v1/review/week` (считает код): по каждой цели факт против нормы в процентах, минуты `leisure`, `social`, `sleep`, доля `unknown`, ночные минуты, три наибольших разрыва. Баланс — минимум и разброс процентов по четырём целям. Цели не ранжируются. Текст обзора собирается из шаблонов кодом.
- Планировщик (этап 7) раскладывает недостающие минуты целей по свободным окнам, но не поверх красного риска раздела 6. В календарь пишется только после подтверждения.
- **Готово, когда:** обзор по реальной неделе на одних данных детерминирован, все четыре цели показаны без главной, `unknown` виден, блоки целей попадают в календарь только по подтверждению.

Как это сделано (шаг 10.6):
- Факт цели — минуты категории из `activity_daily` всех источников; для спорта к ним добавляются минуты тренировок часов. Вклад GitHub и LeetCode — это счётчики без минут, они показываются отдельной строкой и в факт цели не входят. Сон в обзоре — только измеренный часами (`health_daily`). Минуты календарных событий отдельно не прибавляются: время за экраном внутри события уже получает категорию события (слой контекста).
- Нормы: сначала нет, показан факт. Через 14 дней данных сервер предлагает норму: медиана недельных минут по последним четырём завершённым неделям +10 %, округление до 5 минут. Предложение хранится, пока пользователь не ответит («Принять», «Без нормы»). Принятая норма пересматривается раз в 28 дней, снова с подтверждением («Принять» или «Оставить как было»). Норму можно задать и вручную (часы в неделю; 0 убирает норму). Эндпоинты: `GET`/`PUT /v1/goals` (`confirm`, `keep`, `set`, `clear`).
- `GET /v1/review/week` считает код по данным недели: по четырём равным целям факт, норма, процент; минуты `leisure`, `social`, сон по часам, доля `unknown` (выше 20 % — предупреждение), ночные минуты, три наибольших разрыва, баланс (наименьший процент и разброс среди целей с нормой). Текст собирается из шаблонов. Результат пишется в `weekly_review`; одинаковые данные дают байт в байт одинаковый ответ (тест).
- Планировщик: `POST /v1/plan/week` с `{"goals": true}` добавляет блоки по недостающим минутам цели (норма минус факт минус уже запланированное за неделю; крайний срок — воскресенье). Категории в расчёте нагрузки: study → study, sport → hobby, career и work → work. Блок не ставится поверх красного риска: красный недосып отменяет все цели, красное состояние — всё кроме спорта, красный перегруз — учёбу, карьеру и работу; причина показывается пользователю. Спорт по возможности кладётся в сухие светлые окна по прогнозу (дождь меньше 1 мм, между восходом и закатом), иначе в любое свободное. Остальные правила (сон, перерывы, лимиты учёбы, свободные вечера) те же, план проверяет тот же валидатор. В календарь пишется только после «Применить» (`apply` с `{"goals": true}` и тем же `Idempotency-Key`); события называются «Цель: …», в `plan_chunks` они лежат с полем `goal`.
- Экран «Обзор недели» (значок флажка на главной): четыре одинаковые карточки целей, подтверждение норм, разрывы, остальная неделя, кнопка «Разложить недостающее по неделе».

**10.7 Самообновление приложения**

Принято пользователем 29.10.2026. Приложение на телефоне обновляется со своего сервера, без кабеля и Play Store. Тихой установки нет: Android сам показывает подтверждение, пользователь нажимает «Обновить».

Как это сделано (шаг 10.7):
- Ключ подписи — `secrets/release.jks` (копия debug-ключа этого мака с новым паролем: им подписано приложение, уже стоящее на S21+, поэтому переустанавливать с потерей данных не пришлось). Пароль и путь — в `app/android/key.properties`. Оба файла вне git. Потеря ключа = обновление поверх невозможно, только удаление и установка заново; ключ нужно хранить в бэкапе мака. Без `key.properties` релиз подписывается debug-ключом, а `deploy.sh app` такую сборку отказывается выкладывать (сверяет сертификат APK с ключом).
- Сервер: `GET /v1/app/latest` (`version_code`, `version_name`, `sha256`, `size`; 404 с кодом `no_release`, если APK нет или он ещё копируется) и `GET /v1/app/apk` (сам APK). Оба под токеном. Файлы лежат в `/opt/life-agent/app` (`APP_DIR`, по умолчанию `<каталог БД>/../app`), владелец `root:lifeagent`, права `640`; сервис их только читает.
- Выкладка: `deploy/deploy.sh app`. Увеличивает номер сборки в `pubspec.yaml` (больше и локального, и серверного), собирает APK только под arm64 (около 22 МБ), сверяет подпись, кладёт сначала APK, потом `latest.json`. Изменённый `pubspec.yaml` нужно закоммитить.
- Телефон: при запуске, при возврате в приложение (не чаще раза в 6 часов) и кнопкой «Обновление приложения» в настройках спрашивает `/v1/app/latest`. Если `version_code` больше установленного, показывает диалог: скачивает APK в кэш приложения, сверяет размер и SHA-256, отдаёт системному установщику через `FileProvider`. Первый раз Android просит разрешить приложению установку приложений (`REQUEST_INSTALL_PACKAGES`). Ошибки проверки молчат: приложение работает и без обновления. Нативная часть — канал `dev.boomchick.life_agent/update` в `MainActivity.kt`.

## 13. Схемы данных LLM

### Разбор фразы (`/v1/parse`)

Модель возвращает только JSON по этой схеме, без текста вокруг. Модель **не считает даты**: она извлекает части, точную дату и время считает `internal/timeparse` от текущего момента и часового пояса. Сервер валидирует схему, при ошибке действует раздел 3.

Событие:

```json
{
  "kind": "event",
  "title": "КВН",
  "date": {"type": "weekday", "value": "fri", "week": null},
  "time_from": "18:00",
  "time_to": "20:00",
  "duration_min": null,
  "deadline": null,
  "recurrence": null,
  "category_guess": "hobby",
  "missing": []
}
```

Задача с дедлайном:

```json
{
  "kind": "task",
  "title": "Курсовая",
  "date": null,
  "time_from": null,
  "time_to": null,
  "duration_min": 360,
  "deadline": {"type": "weekday", "value": "fri", "week": null},
  "recurrence": null,
  "category_guess": "study",
  "missing": []
}
```

- `date` и `deadline` — один из вариантов:
  - `{"type": "relative", "days": 1}` — «сегодня» (0), «завтра» (1), «послезавтра» (2);
  - `{"type": "weekday", "value": "mon".."sun", "week": "this" | "next" | null}`;
  - `{"type": "absolute", "value": "2026-11-03"}`.
- Правило кода для `weekday` с `week: null`: ближайший такой день, начиная с сегодня; если это сегодня и время уже прошло — через неделю.
- `recurrence`: строка RRULE (RFC 5545), например `FREQ=WEEKLY;BYDAY=FR`. Код проверяет синтаксис.
- `category_guess`: одно из `study`, `work`, `sport`, `hobby`, `rest`, `chores`, `other`.
- `missing`: список полей, которых нет во фразе (`date`, `time_from`, `time_to`, `duration_min`, `deadline`). Если не пусто, приложение спрашивает пользователя, а не гадает.
- Самооценка уверенности модели не используется: она плохо откалибрована. Решение «спросить пользователя» принимается по `missing` и проверкам кода (конец позже начала, дата не в прошлом, дедлайн достижим).
- В промпт передаются текущая дата, день недели и часовой пояс.

### План недели

LLM не участвует (раздел 4). Ответ `POST /v1/plan/week`: `placed: [{item_id, start, end}]`, `unplaced: [{item_id, missing_min}]`.

### Совет

Вход по умолчанию: часы по категориям, цвета календарных рисков, причина совета словами (раздел 3, «Приватность»). Сон и чек-ин добавляются только при включённом переключателе в настройках. Выход: текст до 600 символов, не больше трёх конкретных предложений. Совет не врачебный, диагнозов не ставит; при признаках тяжёлого состояния рекомендует обратиться к специалисту.

Код проверяет ответ: длина до 600 символов, не больше трёх предложений, текст на русском. Не прошёл — действует раздел 3 (повтор, затем следующая модель).

## 15. Экраны Flutter

1. **Главная**: поле ввода (текст, голос через клавиатуру), сверху четыре индикатора рисков, под ними неделя списком по дням. Раз в день сверху карточка чек-ина.
2. **Чек-ин**: энергия 1–5, настроение 1–5, часы сна (только если нет данных Health Connect). Заполняется за 5 секунд.
3. **Карточка**: результат разбора с правкой полей. Для события — вердикт «можно или нет» с причинами и цветами рисков, кнопки «Записать» и «Отмена». Для задачи — длительность, дедлайн, кнопка «Сохранить». Вопрос «это учёба?» показывается здесь.
4. **Неделя**: календарная сетка с цветом по категориям, нагрузка по дням.
5. **План недели**: кнопка «Собрать», предпросмотр, список не поместившихся задач, «Применить» с подтверждением.
6. **Совет**: история советов, кнопка «Попросить совет».
7. **Настройки**: адрес сервера и токен, модель и эффорт для каждой задачи, цепочка резервных моделей, переключатель отправки данных чек-ина и здоровья в совет, пороги, часовой пояс, календари и ICS-ссылка, разрешения здоровья, подсказка по отключению оптимизации батареи, удаление данных здоровья. С этапа 10 добавляются город для погоды, переключатель отправки названий в LLM и ссылка на экран источников.
8. **Источники** (этап 10): список источников с переключателем, временем последней синхронизации и ошибкой, кнопки «Удалить данные источника», «Экспорт», «Удалить всё», инструкция по разрешению UsageStats.
9. **Обзор недели** (этап 10): четыре цели рядом (факт, норма, процент), `leisure`, `social`, `sleep`, доля `unknown`, три наибольших разрыва, подтверждение предложенных норм, кнопка «Разложить недостающее по неделе».

Состояние ошибок: нет сети, сервер недоступен, лимит модели. Приложение показывает понятное сообщение и сохраняет введённый текст, чтобы его не терять.

## 16. Тесты и проверка

- Go, таблицы случаев, LLM заменяется заглушкой:
  - `internal/timeparse`: фиксированное «сейчас», все варианты `date`, «пятница» в пятницу до и после указанного времени, переход на летнее время, конец года;
  - `internal/load`: правила нагрузки, события на весь день, серии, нет данных → серый;
  - `internal/plan`: детерминированность (один вход → один выход), отсутствие нарушений по валидатору, корректный `unplaced`;
  - `internal/llm`: переход по цепочке резервных моделей на заглушках провайдера (невалидный JSON, лимит модели, дневной лимит аккаунта останавливает цепочку, таймаут, цепочка исчерпана, потолок вызовов на запрос), проверка ответа совета, перевод эффорта в параметры провайдера;
  - пересечения и идемпотентность `POST /v1/events`;
  - этап 10: слои категоризации (порядок, порог уверенности, `unknown`), разность накопительных часов Steam, отсутствие названий окон и URL в БД, логах и теле запросов, отбрасывание ответа LLM вне списка категорий, детерминированность `GET /v1/review/week`, удаление по источнику и `DELETE /v1/data`.
- Календарь: интеграционная проверка на отдельном тестовом календаре, а не на основном календаре пользователя.
- Разбор фраз: эталонный набор из 30–50 типовых фраз с ожидаемым результатом (события, задачи, повторы, неполные фразы). Прогон при каждой смене модели или промпта, порог из раздела 14. Прогон идёт с паузой между запросами и помечается `source = eval`. Если квоты на день не хватает, прогон продолжается на следующий день с места остановки.
- Flutter: проверка вручную на S21+ по критерию «Готово, когда» каждого этапа, плюс виджет-тесты на карточку и чек-ин.
- После выкладки: соседние сайты на `cv-prod` открываются, `nginx -t` проходит, память сервера не выросла выше нормы.

## 17. Безопасность

- Токен доступа не короче 32 случайных байт, сравнение за постоянное время, ограничение частоты запросов (rate limit) на `/v1/*`.
- Только HTTPS. Токен в приложении хранится в защищённом хранилище (`flutter_secure_storage`).
- Ключ сервисного аккаунта имеет доступ только к календарям, перечисленным в конфиге.
- В логах и в `llm_calls` нет токенов, ключей, текстов задач и данных здоровья.
- Данные здоровья: только дневные сводки, удаление из приложения (`DELETE /v1/health`).
- Бэкапы с данными здоровья: права `600` на сервере, `700` на каталог на маке.
- Токен утёк: заменить в `.env` и в приложении, перезапустить сервис.

### Модель угроз (этап 10)

Защищаем поведенческий профиль: когда пользователь спит, что делает за компьютером и телефоном, во что играет. Защита рассчитана на одного пользователя и обычного злоумышленника. Не защищаемся от: root-доступа к серверу, физического доступа к разблокированному телефону или Mac, целевых атак уровня государства.

| Угроза | Мера |
|--------|------|
| Утечка токена доступа к API | Раздел 17 выше: токен не короче 32 байт, rate limit, ротация. Через токен виден весь профиль, поэтому ротация обязательна при любом подозрении |
| Кража файла БД или бэкапа | Хранятся только дневные суммы; срок хранения раздела 14; бэкапы шифруются `age` публичным ключом на сервере, приватный ключ только на маке (сервер не расшифрует свои бэкапы). Шифрование колонок ключом с того же сервера не вводится: оно не защищает от взлома сервера |
| Взлом соседнего проекта на `cv-prod` | Раздел 9: отдельный пользователь `lifeagent`, права `600` и `700`, `ProtectSystem=strict`. Секреты других проектов не читаются, наши недоступны им |
| Утечка внешних токенов (GitHub, Steam key) | Только в `.env` с правами `600`, не в БД и не в логах. GitHub: fine-grained токен только на чтение, срок до 90 дней, ротация по календарю. Steam key можно перевыпустить |
| Провайдер LLM логирует запросы | В LLM уходят только названия неизвестных приложений, игр и доменов (раздел 3), без времени и других данных использования. Переключатель отключает отправку |
| Prompt injection через названия приложений, игр, доменов | Названия — недоверенный ввод. Ответ принимается только как значение из фиксированного списка категорий, проверка схемой, остальное отбрасывается |
| Заголовки окон и URL на Mac | ActivityWatch хранит их локально. Требуется FileVault. Наружу уходят только категории и минуты, проверка тестом |
| Данные на телефоне | Сырые данные UsageStats не хранятся после отправки; токен в `flutter_secure_storage` |
| Данные остаются после отказа от источника | Удаление по источнику, полный `DELETE /v1/data`, `GET /v1/export` |
| Логи | Нет токенов, ключей, названий окон, URL и заголовков (раздел 17) |

Публичный профиль Steam и так виден всем; новый риск только в том, что мы связываем его с остальными данными.

## 18. Риски и запасные варианты

| Риск | Что делаем |
|------|-----------|
| Дневной лимит бесплатных моделей кончается | Потолок вызовов на запрос, счётчик квоты в настройках, автосовет уступает квоту разбору; если не хватает регулярно — пополнение на $10 по решению пользователя |
| Бесплатные модели нестабильны или исчезают | Цепочка резервных моделей, провайдеро-независимый конфиг, эталонный набор показывает, что сломалось |
| Ни одна бесплатная модель не даёт 90 % на эталонном наборе | Обсудить с пользователем: дешёвая платная модель OpenRouter, упрощение схемы или подсказки в интерфейсе |
| OpenRouter недоступен | Приложение сохраняет введённый текст; другой OpenAI-совместимый провайдер добавляется конфигом |
| Модель неверно разбирает фразы | Журнал `llm_calls` и эталонный набор, правка промпта или смена модели |
| Мало памяти на сервере | Лимит 300 МБ на юнит, Go-бинарник лёгкий, при нехватке обсудить swap с пользователем |
| One UI убивает фоновую задачу | Отключение оптимизации батареи; запасной вариант — push через FCM |
| Samsung Health не отдаёт данные в Health Connect | Проверить на этапе 8 заранее; часы сна остаются в чек-ине |
| Напоминания не работают у событий, созданных сервисным аккаунтом | Проверка на этапе 2; запасной вариант — явные `reminders` в событии или OAuth |
| Метрика учёбы занижена (учёба вне календаря) | Планировщик кладёт учебные задачи в календарь, чек-ин даёт прямой сигнал |
| Let's Encrypt отказывает для `sslip.io` | Поддомен `semenovm.ru` |
| Голосовой ввод клавиатуры плохо справляется с названиями | `speech_to_text` или серверное распознавание через Whisper |
| Задачи не помещаются в неделю | Список `unplaced` с недостающим временем, решает пользователь |
